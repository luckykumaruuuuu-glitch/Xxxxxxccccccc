PHASE 1: bugs (TransferWorker, WedFacesApi, models)
1. One bad file must never stop the batch. Handle each item on its own: permanent errors (HTTP 400, 403, 404, 413, 415) mark ONLY that item FAILED with the reason and the worker continues with the next item. Retryable errors (IOException, 408, 429, 5xx) retry with exponential backoff, respect the Retry-After header, max 5 attempts per item. A 401 after a failed refresh pauses the whole batch with "Sign in again" and keeps the files.
2. Import result reconciliation: if the server status contains a "results" array (new server), mark each item from its own result (match by uploadId, then fileName). Otherwise (old server) never mark the whole batch "needs review" because of failures that name files from other batches; show "N other failures on the server" as a note and mark items IMPORTED only when the status has no failures at all.
3. Upload up to 3 files in parallel (a constant), reuse the OkHttp client, and keep the per-file progress in the queue.
4. Write the unit tests: one bad file does not block others, 413 and 415 are per-item, 429 with Retry-After, 401 refresh failure pauses, status reconciliation old/new. Use work-testing (TestListenableWorkerBuilder) and MockWebServer. Add a queue database migration test.

PHASE 2: background and flow
1. Pipeline: download one original from the camera, then enqueue its upload at once. Do not wait for all downloads. Trigger the server import after every 25 uploaded files or 20 seconds without a new file, and at the end; never start an import while one is running for that album.
2. Foreground: run camera downloads in a foreground service (declare the correct foregroundServiceType and permissions for Android 14 and 15, request POST_NOTIFICATIONS) and give upload workers setForeground with a progress notification ("Uploading 12 of 200", Pause and Cancel actions). Add a "Keep screen on during transfer" switch.
3. Camera card listing: do not fetch thumbnails for all items at once. Load thumbnails lazily for visible tiles only, with a small cache and low priority, and let a download always take priority over thumbnails (they currently share one lock). Add "last 50 / 100 / all" and "only new since last send".
4. Remember what was already sent (camera object name + size + capture time) in the database, mark "Already sent" in the UI, allow resend.
5. RAW and video: show them as "not supported by the server" and filter them out. If a RAW+JPEG pair exists, pick the JPEG.

PHASE 3: upload-only key (needs the new server endpoints: X-Upload-Key, GET /api/upload-key/album, results array in the import status)
1. Settings accepts a key by scanning the QR (JSON {"server","albumId","key"}; use a library whose license you verified, e.g. ZXing based) or by pasting. Store the key in the existing Keystore-encrypted store. With a key the app skips login and the album list, and sends X-Upload-Key on the three import routes. Keep the old login mode working.
2. Clear stored credentials when the key is revoked (401 with a key means "revoked, ask for a new key").

PHASE 4: universal folder-watch mode (works with Canon Camera Connect, Sony Imaging Edge, SnapBridge and any app that saves photos on the phone)
1. The operator picks a folder with the Storage Access Framework (ACTION_OPEN_DOCUMENT_TREE) or DCIM via MediaStore. Observe MediaStore with a ContentObserver plus a periodic WorkManager scan of the chosen tree. Queue only new JPEG/PNG/WEBP files, skip files that existed before activation unless "include existing" is chosen, skip files still being written (IS_PENDING, size not stable for 2 seconds), and remember processed document IDs.
2. This mode uses the same queue, upload and import code. Label it clearly in the UI.
