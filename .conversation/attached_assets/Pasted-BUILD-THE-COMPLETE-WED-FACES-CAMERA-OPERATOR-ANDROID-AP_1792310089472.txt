3. Main objective

The photographer connects a supported camera to the Android phone, browses the photos stored on the camera memory card, selects specific images, and sends only those selected originals to the correct WED Faces album.

The main workflow must be:

1. Configure the WED Faces server URL.
2. Log in with the user's existing WED Faces credentials.
3. Load real albums from the server and select one.
4. Connect a supported camera.
5. Retrieve the real camera file listing and available thumbnails.
6. Select individual or multiple photos.
7. Tap Send Selected.
8. Download or stream only the selected original files.
9. Upload them to the selected WED Faces album.
10. Trigger the album import and display its actual server-side status.

Every visible button must perform a real action. If a feature is unavailable, display the reason instead of pretending it succeeded.

5. Camera Wi-Fi and internet connectivity

Camera Wi-Fi and internet access must be handled carefully.

- Allow the user to initiate a supported camera network connection using Android's network APIs and permission dialogs.
- Where manual Wi-Fi connection is required, give clear on-screen instructions.
- Bind camera PTP/IP sockets to the camera's Wi-Fi network when required.
- Do not bind the entire Android process to the camera network if doing so would break internet access for WED Faces API requests.

- Detect when the camera network has no internet.

- Do not repeatedly request Android permissions after the user has already denied them.

6. WED Faces server integration

Use the existing WED Faces API. Do not create a new backend, modify server endpoints, or invent undocumented authentication methods.

The server base URL must be configurable in the app. Never hardcode a production server, password, private access token, or API secret.

Login

"POST /api/auth/login"

JSON body:

"{"email":"USER_EMAIL","password":"USER_PASSWORD"}"

Parse the actual server response, including available "accessToken", "refreshToken", "expiresIn", and user information.

Persist authentication securely on the Android device. Do not log passwords or tokens. Handle invalid credentials and expired sessions correctly.

Refresh session

"POST /api/auth/refresh"

JSON body:

"{"refreshToken":"SAVED_REFRESH_TOKEN"}"

Use this endpoint according to the server's actual contract. Handle refresh failure by asking the user to log in again.

Fetch albums

"GET /api/albums"

Use the authenticated request and display the real returned albums.

Allow the user to select an album. Store and use the album's actual "id", not its name or "publicId".

Do not proceed with uploads until a valid album is selected.

Upload selected images

For each selected supported original file, call:

"POST /api/albums/{albumId}/import/upload"

Use multipart/form-data containing:

- "uploadId": a persistent UUID for that upload operation
- "file": the actual selected image file

Use the server's real response. Preserve the same upload ID across retries of the same operation where required. Avoid loading large images entirely into RAM.

The existing server contract supports JPG, JPEG, PNG, and WEBP imports. Do not falsely report ARW, CR3, NEF, or video files as supported by this import endpoint. Show an understandable explanation for unsupported formats.

Respect the server's configured file-size limit. The documented default is approximately 30 MB, but deployments may differ. Handle size-limit responses such as HTTP 413 clearly.

Trigger import

After all applicable files in a batch have uploaded successfully, call:

"POST /api/albums/{albumId}/import"

JSON body:

"{"path":".device-uploads/{albumId}"}"

Replace "{albumId}" with the real selected album ID.

Do not invent a different import path or substitute a public album identifier.

Track import status

Poll:

"GET /api/albums/{albumId}/import/status"

Parse and display the actual returned fields when present:

- "state"
- "total"
- "imported"
- "duplicates"
- "failed"
- "failures"
- "error"

Handle "NONE", "RUNNING", "COMPLETED", and "FAILED" correctly.

Stop polling when a terminal state is reached. Use reasonable backoff and provide a manual refresh action. Never mark an import complete merely because the image upload request returned successfully.

Keep upload completion and server import completion as separate states.

7. Transfer queue — fully functional

Implement a persistent queue that survives navigation, app restarts, and recoverable network failures.

Each queue item should have a real state, such as:

- Selected
- Waiting for camera
- Downloading selected original
- Waiting for internet
- Uploading
- Uploaded; waiting for import
- Imported
- Failed; retry available
- Unsupported format

Show the filename, status, and meaningful progress where available.

Requirements:

- Retry failed operations safely.
- Prevent duplicate queue entries for the same pending operation.
- Preserve upload IDs for retries.
- Allow the user to cancel queued work safely.
- Do not claim that cancellation reversed an upload that the server already accepted.
- Do not delete the camera's original under any circumstances.
- Keep temporary files only when needed for a pending transfer or retry.
- Clean up app-created temporary originals after the corresponding operation reaches a safely completed state.
- If the phone loses its connection to the camera, explain whether a selected original still needs to be retrieved.
- If internet is unavailable, queue uploads instead of silently discarding work.

Use Android-supported background work and notifications where appropriate and compatible with the generated project.
